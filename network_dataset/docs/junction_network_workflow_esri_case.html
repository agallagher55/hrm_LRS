Building the Junction Network from LRS Data

Prepared 2026-09-15 for Ryan Lowe, to relay to Sukhjit P. at Esri Canada · Case #04248942 – ArcGIS Pro – LRS Errors

Compiled from what is committed to this repository. Network execution evidence runs to 2026-09-03; the editing evidence in the last section is from Robbie Evans on 2026-09-11.

What Esri asked for Esri's 2026-09-01 and 2026-09-09 emails ask the same two things twice: (1) the high-level workflow the coworker follows to create the junction network, and (2) any error messages hit along the way, with screenshots. The "coworker" is Alex Gallagher, and the workflow is the one documented here. Esri's read so far is that the behaviour is data-specific, not version-specific, and the evidence below is consistent with that.
Terminology: what the case calls the "junction network" is the ArcGIS network dataset TRNLRS_street_network, built inside the feature dataset SDEADM.TRNLRS_network. Junctions are one of its three sources. The small intersection errors matter because network datasets connect edges by coincident endpoints, so a segment that overshoots or falls short of an intersection does not form a junction there at all.

1 Build the edge source from the LRS

Script: scripts/LRS_updates.py. Runs on the LRS refresh cycle.

arcpy.locref.OverlayEvents overlays LRSN_Route with seven event tables to produce TRNLRS_segmented_street_events. A SQL query layer then joins E_AddressRange for audit dates and filters to TO_DATE IS NULL (active streets only). The result is truncated into and appended to SDEADM.TRNLRS_TRN_STREET_VW, a real standalone SDE feature class despite the _VW suffix.

Roughly 18,600 edge features citywide. This is the step that produces the geometry Esri is looking at. The street segments the network consumes are reconstructed from route measures, they are not hand-digitized street centrelines.

A QC pass runs before anything downstream: duplicate FDMID, null FDMID, null GSA, and segments below a short-segment threshold. It does not currently check for dangles or for segments that overshoot an intersection, which is the class of defect this case is about.

2 Copy the three sources into one feature dataset

Script: network_dataset/scripts/03_create_network_dataset.py, copy_fc_to_fd().

ArcGIS requires every network source to live inside the same feature dataset, and SDE enforces unique feature class names across the whole geodatabase, so the standalone _VW class cannot simply be moved. Three arcpy.management.CopyFeatures calls:

  • SDEADM.TRNLRS_TRN_STREET_VW (Prod) → SDEADM.TRNLRS_network\TRNLRS_TRN_STREET
  • SDEADM.TRN_streets_routes\TRN_street_junction → SDEADM.TRNLRS_network\TRNLRS_street_junction
  • SDEADM.TRN_streets_routes\TRN_traffic_turn → SDEADM.TRNLRS_network\TRNLRS_traffic_turn

The junction and turn classes are carried forward unchanged from the legacy TRN_street_network, which was built on the old hand-maintained TRN_street centrelines. That mismatch (legacy junctions and turns against LRS-derived edges) is the origin of most of the findings in the next section.

3 Remap the turn feature class onto the new edge ObjectIDs

Script: network_dataset/scripts/05_rebuild_traffic_turns.py, verified by verify_turn_rebuild.py.

A turn feature stores its edge references as Edge{N}FID, which is the OBJECTID of a feature in the registered edge source, plus Edge{N}FCID (the source class ID) and Edge{N}Pos. Copied straight across, every one of those OBJECTIDs points at a feature in the old TRN_street class and means nothing in TRNLRS_TRN_STREET.

The remap resolves each turn spatially: find the junction shared by the old Edge1 and Edge2 geometry, find the new edges meeting at that junction, break ties by local tangent bearing and by the turn feature's own recorded point, and write the new OBJECTIDs. It writes to a staging class first, and an independent ten-check verifier runs before anything is swapped in.

Latest QA run: 1,238 input turns, 1,189 written (4.0% skipped, reasons logged per category), 99.7% agreement with the source's own Edge1End values, all ten verifier checks clean.

4 Create the network dataset

Originally arcpy.na.CreateNetworkDatasetFromTemplate; since 2026-09-01, Pro's interactive New Network Dataset wizard.

The original path exported an XML template off the legacy network with CreateTemplateFromNetworkDataset, edited it (renamed sources, cleared elevation field references), and recreated from it. That path is currently blocked, see ERROR 030386 in the error table.

QA's current network dataset was therefore created by hand: right-click SDEADM.TRNLRS_network → New → Network Dataset, add the three sources, configure attributes and evaluators, finish.

5 Configure connectivity, attributes, and evaluators

  • Connectivity: endpoint only, one connectivity group, version 1 policy on both edge and junction sources.
  • Elevation: NetworkElevationModel = 0 (none). The LRS pipeline does not segment elevation, so FROM_ELEV / TO_ELEV do not exist on the new edge source and all elevation field references were cleared. This matters for this case: with no elevation model, connectivity is decided purely by whether two endpoints coincide.
  • Length cost attribute, metres, Python Field Script !Shape! on both directions.
  • OneWay restriction, prohibited, Python Field Script reading STR_DIR.
  • TrafficTurn restriction, prohibited, constant True on the turn source.
  • Directions: Base Name → STR_NAME, Suffix Type → STR_TYPE, Full Name → FULL_NAME.

6 Build the network

arcpy.na.BuildNetwork, or Build Network in Pro with Force Full Build checked. A full build of this network (about 37,700 edges) completes in roughly 90 seconds to two minutes.

This is the step that emits BuildErrors_<guid>.txt, which is where the junction and turn geometry problems actually surface.

7 Grant SQL Server permissions

OS-authentication users cannot open the network dataset until PUBLIC SELECT is granted on two families of backing tables (N_<id>_* metadata and ND_<id>_* dirty-area tracking) plus the four source feature classes. Registration IDs are per network dataset instance and change on every delete-and-recreate.

8 Validate with real solves

Route and Service Area solves with OneWay and TrafficTurn explicitly enabled in the layer's Travel Mode. A clean build message alone proves nothing about whether restrictions are enforced.

9 Steady state after each LRS refresh

Each LRS refresh truncates and reloads TRNLRS_TRN_STREET_VW, so the feature dataset copy goes stale. The copy is re-synced with DeleteRows + Append and the network rebuilt. This part is coded but has not been deployed to Prod yet.

Where the intersection geometry actually bites

This is the part of the workflow that connects to Esri's case. Five independent pieces of evidence, listed strongest first.

Strongest evidence Nine turn restrictions rejected at build with Cannot find at junction

On the 2026-09-01 QA build, 9 of 1,189 remapped turn features (0.76%) failed to become live turn elements:

Source table [SDEADM.TRNLRS_traffic_turn], Object ID [N]: Cannot find at junction.

Each of the nine was diagnosed directly against the live data, measuring the true minimum distance across all four first-point / last-point pairings between the turn's consecutive edges:

  • Seven of nine: a real gap of 0.006 m to 0.41 m between two consecutive edges in TRNLRS_TRN_STREET that should meet at one junction. Our remap's snap tolerance is 0.5 m, so the remap accepted the pair as adjacent, but the network's XY tolerance is 0.001 m, so Build Network would not merge them into a single junction. These are genuine pre-existing digitizing gaps in the edge source, at exactly the scale this case is about.
  • Two of nine: an exact 0.0000 m coincidence that still failed. Unexplained. This is the one finding we would most like Esri's opinion on, since coincident endpoints within XY tolerance should build a junction.

Practical impact: up to 9 prohibited-turn restrictions go unenforced in solves. Every edge and every other turn built correctly.

Independent confirmation, large scale Roughly 500 streets flagged during editing (Robbie Evans, 2026-09-11)

During expert acceptance testing of the QA network, Robbie Evans found streets that "aren't getting calculated due to dangles in the segments when editing," and stopped testing after about 500 were flagged. His characterisation of the majority: "Most of the ones I've looked at are just simple fixes though. The segment is extended past the intersection."

A segment extended past an intersection is precisely the failure mode the previous item describes at sub-metre scale, seen here at editing scale and at much higher volume. Testing is paused until these are corrected in the LRS source; the list is going to Melanie Parker.

This is new information that post-dates everything else in this document and was not available when the case was opened. It is the single best argument that the behaviour is data-specific rather than version-specific.

Citywide audit 249 route intersections with no aligned edge endpoint

network_dataset/scripts/06_check_junction_alignment.py is a read-only diagnostic that compares every TRNLRS_TRN_STREET edge endpoint against SDEADM.INT_RouteOnRoute, the Route Intersection Class generated independently from LRSN_Route by arcpy.locref.GenerateIntersections. Run citywide on 2026-08-31:

249active route intersections with no edge endpoint within 1 cm
221of those with no edge endpoint within 10 m at all
28matched but misaligned, 0.03 m to 10.0 m

It is not a systematic coordinate transform. The offset vectors point in every direction with no shared sign or ratio, for example (-0.445, 9.984), (-8.973, 2.663), (9.165, -0.516), (-3.612, -7.914) on the four largest. A transform bug would repeat one vector or a small family of them. The pooled mean is near (0, 0) with large standard deviation, which is what unrelated small errors look like. This was worth establishing because three hand-picked spot checks had originally suggested otherwise.

Most of it is explained. Both the no-match population and the largest offsets are dominated by highway ramps and interchanges (ALM-A RAMP, HIGHWAY 102 NB EXIT 4B OFF RAMP, HIGHWAY 111 WB EXIT 6 ON RAMP). With no elevation model, a highway passing over a ramp is flagged as a crossing by the route intersection class but correctly has no shared edge endpoint at street level. That is an accepted limitation of this network, not a defect.

Four are not explained. Plain surface-street pairs with no grade-separation excuse, and real candidates for a defect in the edge geometry:

  • Hemlock Dr / High Timber Dr – 8.7 m
  • Wright Ave / Countryview Dr – 9.36 m
  • Skreia Rd / Sailview Lane – 6.26 m
  • Massachusetts Ave / Lady Hammond Rd – 7.44 m
Expected but worth reporting Hundreds of standalone junction warnings on every build

Every build writes a large number of these into BuildErrors_<guid>.txt:

Standalone user-defined junction is detected

for TRNLRS_street_junction. Cause: the junction class was carried forward from the legacy network, where it was placed against the old hand-maintained centrelines. LRS resegmentation moved edge endpoints, so those manually placed junctions are no longer coincident with any edge. They are ignored during solves and do not affect results, but the count is itself a measure of how far the LRS-derived endpoints have drifted from the legacy intersection positions, which may be useful to the case.

Related data-quality finding One edge digitized backwards relative to its real-world sign

Bishop St between Barrington St and Hollis St (TRNLRS_TRN_STREET OID 12002) carries STR_DIR = 'FOTD', and the one-way evaluator reads it correctly, but the line geometry is digitized in the opposite direction to the real-world one-way sign. Along Digitized and Against Digitized therefore map to the wrong compass direction on that one edge. Confirmed with HRM's GIS team on 2026-09-03. It is a source-geometry issue, not a network dataset issue. Scope is unknown; only this one edge has been checked.

What this document cannot answer

Stated plainly so nothing here reads as more settled than it is.

  • The two exact-coincidence turn failures. Genuinely unexplained. Build Network's error attribution during turn-element creation may not be strictly one-to-one, so it is worth checking whether a third turn references the same shared edge, but that has not been done.
  • The datum warning. Nobody has checked the editing map for it. The statement above is about the build-side datasets only.
  • The three original spot-check intersections (Blowers/Barrington, Barrington/Salter, Upper Water/Hollis) do not appear by name in the 28 misaligned rows or in the sample of no-match rows that was printed. Whether they came in aligned or are simply buried in the roughly 200 unprinted rows has never been checked with a targeted query.
  • Robbie's roughly 500 errors have not been seen by this repository. The characterisation above is from his email. There is no list, no FDMIDs, and no overlap analysis against the four plain-street anomalies or the seven sub-metre gaps. That overlap would be worth doing once Mel has the list.
  • The full 249 no-match set has never been classified. The grade-separation conclusion is from a 20-row sample judged by name, not from a heuristic run over all of them.
  • Whether these errors are caused by the LRS pipeline or predate it has not been established. The edge geometry is reconstructed from route measures by OverlayEvents, so a defect could be in LRSN_Route, in the event data, or introduced by the overlay itself. Nobody has compared a sample of flagged locations against the legacy TRN_street geometry to find out, and that is probably the single most useful next diagnostic for this case.
