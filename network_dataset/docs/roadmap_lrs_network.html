TRNLRS Street Network: Build Roadmap

Prepared 2026-09-09 · Reflects repository state at commit 4420ec6 (2026-09-08) · Latest network execution evidence in the repo is dated 2026-09-03

This page is compiled entirely from what is committed to this repository (docs, scripts, data outputs). It is not a live query of Dev, QA, or Prod. Where the current QA environment and this page disagree, QA is the authority.

Where things stand QA has a working, editable network dataset, and both hard restriction types (one-way and prohibited turns) are proven correct with real solve tests. That was the hard part, and it is done. What is left is acceptance testing, a handful of data-policy decisions that need a business owner rather than an engineer, and turning the rebuild into something that survives a Prod cutover unattended. Dev still runs the original VBScript-based build and cannot be edited in place. Prod has nothing built yet. Treat this as late validation and pre-production, not production-ready.

How the network is built

The network's edge source is derived from the LRS dynamic-segmentation pipeline, then copied into a dedicated feature dataset alongside the junction and turn sources so ArcGIS can build a network dataset on top of them.

The copy step exists because SDE requires unique feature-class names across the whole geodatabase (the standalone _VW name can't be reused inside the feature dataset) and because all network sources must live in the same feature dataset. The standalone _VW class stays authoritative; everything inside TRNLRS_network is a derived copy that goes stale on every LRS refresh and has to be re-synced and rebuilt.

What's complete

Organized by the phases used throughout network_dataset/docs/network_build_status.md and network_dataset/docs/network_dataset_migration_plan.md. Click a phase to expand it.

Done Phase 1: Extract the legacy network configuration

network_dataset/scripts/01_extract_network_config.py ran against the old TRN_street_network and produced network_dataset/data/network_config.json and network_dataset/data/network_template.xml.

Caveat carried forward: the exported template turned out to be an incomplete snapshot. It was captured before someone hand-fixed the OneWay evaluator directly in Pro's Properties dialog, so the file didn't reflect what the live networks actually ran. See Phase 6 below for the fix.

Done Phase 2: Schema comparison (old edge source vs. LRS-derived edge source)

network_dataset/scripts/02_compare_schemas.py produced network_dataset/data/schema_comparison.json and network_dataset/data/evaluator_field_map.json. FROM_ELEV/TO_ELEV were the only fields with real impact (both referenced by the old elevation model); every other schema difference was confirmed harmless.

Known bug, low current risk: evaluator_field_map.json is empty, and the docs originally explained that as "no field evaluators to check." The real reason is a key-mismatch bug in map_evaluator_fields(): it reads ev.get("field_name"), a key that script 01 never writes, so the check silently returns nothing before it can run. The conclusion (the evaluators are safe against the new source) is still correct, it was just verified by hand instead of by the automated check that's supposed to catch this. That automated net stays dead until someone fixes the key names, and it's exactly the check that should catch a regression when a travel-time attribute is eventually added.

Done Phase 3: Edit the XML template

Names updated to the TRNLRS_* sources, elevation field references cleared (FromElevationFieldName/ToElevationFieldName/ElevationFieldName), NetworkElevationModel set to 0 (none). This is what let the first Dev/QA builds succeed with endpoint-only connectivity.

Mixed by environment Phase 4: Create and build the network dataset
✅ QArebuilt from scratch 2026-09-01
⚠️ Devoriginal 2026-06-26 build, read-only
❌ Prodnothing built

The original path (network_dataset/scripts/03_create_network_dataset.py + network_dataset/data/network_template.xml) built Dev and QA cleanly on 2026-06-26. That template later turned out to have two problems that only surfaced during the 2026-09-01 turn-FC swap:

  • Its Length/OneWay evaluators are VBScript. ArcGIS Pro 3.5 refuses to build a network dataset from a VBScript-bearing template at all (ERROR 030386).
  • Any network dataset that already carries VBScript evaluators opens as permanently read-only starting in Pro 3.4, by Esri's own deliberate design (confirmed against Esri KB 000034955 / FAQ 000034321, and against four other hypotheses that were tested and ruled out: stale locks, Pro version, project state, schema version).

QA's network dataset was rebuilt from scratch using Pro's interactive New Network Dataset wizard with Python evaluators, since CreateNetworkDatasetFromTemplate against the old XML would just reproduce the same error. Dev's original network dataset is untouched and still locked read-only; it needs the identical from-scratch treatment, not an edit.

Done for QA Phase 5a: Traffic turn rebuild

Turn features store edge references as the OBJECTID of a feature in the registered edge source. When the turn class was copied against the new LRS-derived edge source, every reference pointed at an OBJECTID that no longer meant anything, so every turn failed at build time. network_dataset/scripts/05_rebuild_traffic_turns.py spatially remaps each turn's edge references onto the new edge source by geometry, and network_dataset/scripts/verify_turn_rebuild.py independently checks the result with 10 mechanical checks before anything gets swapped into place.

The script was substantially rewritten on 2026-08-31 after review found the original junction-detection logic was built on a wrong assumption about Esri's Edge#Pos field (it collapses to a constant 0.5 under this network's connectivity settings, so a script that branched on it was effectively picking the same endpoint for every record). The rewrite derives the junction directly from shared edge geometry instead, uses the turn's own recorded point to break ties at divided roads, and only writes a turn when every populated edge slot actually resolved.

Lesson worth repeating: defining OneWay/TrafficTurn on the network dataset does not make any given Route or Service Area layer honor them. That's controlled per Travel Mode (Route layer → Travel Mode → Edit → Restrictions tab), and a freshly created layer's default travel mode does not pick up custom restrictions automatically. A solve will silently drive straight through a real prohibited turn or the wrong way down a one-way street, with no error, if the box isn't checked.

The one-way debugging saga, summarized: the evaluator logic itself was correct on the first attempt, but nothing changed in any solve no matter how the script was written, including a version hardcoded to unconditionally block every edge network-wide. The actual root cause: Force Full Build was not checked after editing the evaluator's script content. An incremental build leaves the network's precomputed per-edge weight tables stale with no error or warning of any kind, so the solver keeps using old cached values regardless of how the evaluator reads. Once Force Full Build was used, the hardcoded version immediately produced the expected "no solution found" error. That forced rebuild then hung for 18 hours on a genuine blocking session on QA's shared SQL Server (eventually killed by a DBA), a separate lesson now captured in CLAUDE.md. The fix was verified for real only after a discriminating two-way-street test (Barrington St, ordinary two-way, clean in both directions) ruled out a lingering hardcoded-True regression that a one-way-only test could not have distinguished from correct behavior.

Done for QA Phase 6: Rebuild and re-export the network template

Before the VBScript logic on Dev became unrecoverable, the authentic OneWay logic was pulled back out of Dev's live network with CreateTemplateFromNetworkDataset (2026-09-01):

' Along Digitized                          ' Against Digitized
restricted = False                          restricted = False
Select Case UCase([STR_DIR])                Select Case UCase([STR_DIR])
  Case "N", "FDTO", "T": restricted = True    Case "N", "FOTD", "T": restricted = True
End Select                                  End Select

FDTO blocks travel along the digitized direction, FOTD blocks travel against it, and N or T block both directions. The domain was confirmed complete on 2026-09-03: BOTH (15,812 rows), FOTD (2,792), NULL (7), FDTO (1). Nothing exists beyond what the evaluator already handles.

The corrected Python translation was applied to QA, verified with the one-way solve test above, exported with CreateTemplateFromNetworkDataset, and committed over network_dataset/data/network_template.xml on 2026-09-03.

Open: nobody has actually confirmed CreateNetworkDatasetFromTemplate can build from this corrected, Python-evaluator template. QA's rebuild was done by hand in the interactive wizard. Until this runs successfully, there is no proven automated rebuild path, which is the top item in the roadmap below.

Coded, not deployed Refresh automation

network_dataset/scripts/04_sync_and_rebuild_network.py and sync_network_edge_source() inside scripts/LRS_updates.py re-copy the edge source into the feature dataset and rebuild the network after every LRS refresh. Both correctly use DeleteRows rather than TruncateTable for the controller-dataset-safe re-sync.

Known bug, confirmed still present in the code today: a separate, older helper inside LRS_updates.py, append_feature(), still calls arcpy.TruncateTable_management() directly. TRNLRS_TRN_STREET is a controller-dataset member, so this will raise ERROR 001395: Operation not supported on a feature class in a controller dataset the first time it actually runs against it. It hasn't surfaced yet only because LRS_updates.py has never been deployed to prod.

LRS_updates.py has not been deployed to E:\HRM\Scripts\Python\LRS_updates.py, and no full LRS refresh cycle has been run end-to-end with the network sync included.

1 Establish the current live baseline

The repository's docs are several days ahead of the last time anything was actually queried live. Cheap to do, and it's the foundation everything after this decision rests on.

  • In QA, confirm directly: network build date, source feature counts, turn count in Properties, current evaluator definitions, and a fresh BuildErrors_<guid>.txt

2 Prove the automated rebuild path

Right now the only way to build this network dataset correctly is the manual interactive wizard. Nothing about this project survives a Prod cutover, or a future evaluator change, without a rebuild path that doesn't depend on someone remembering 6 wizard steps.

  • Test CreateNetworkDatasetFromTemplate against the corrected Python-evaluator network_dataset/data/network_template.xml (never actually tried in this project)
  • Fix LRS_updates.py's append_feature() to use DeleteRows instead of TruncateTable before it ever runs against prod
  • Decide the turn-OID-stability question: an LRS refresh truncates and reloads TRNLRS_TRN_STREET, which reassigns every row's OBJECTID and silently breaks every turn's edge reference. The documented claim that "turns don't need rebuilding on each refresh" is incorrect. Pick one: remap turns every refresh cycle, make edge OBJECTIDs stable via a keyed update instead of truncate/reload, or store turns against a stable street-identity key and re-derive edge references at build time.
  • Run network_dataset/scripts/run_full_network_rebuild.py end to end in a non-production environment
  • Deploy the updated LRS_updates.py, but only after Prod's feature dataset and network actually exist

Definition of "ready for Prod," proposed for discussion

None of these are checked off yet. This is the bar, not a status report.

  • Corrected Python template successfully creates and fully builds a fresh non-Prod network
  • Agreed representative Route and distance Service Area comparisons pass against the legacy network
  • One-way and prohibited-turn smoke tests pass with restrictions enabled in the Travel Mode
  • Address-range / geocoding checks pass
  • Every build warning is counted and dispositioned; the 9 rejected turns are fixed or formally accepted
  • Grade-separation and road-exclusion decisions are recorded
  • A full LRS refresh plus edge sync/rebuild passes in rehearsal
  • Prod feature dataset, remapped turns, permissions, monitoring, and rollback steps are documented with named owners
Operational gotchas worth remembering before touching Dev or Prod (from CLAUDE.md)
  • arcpy.na.CreateTurnFeatureClass takes out_location / out_feature_class_name, not out_name. Use in_template_feature_class to match an existing turn FC's schema without registering the output as a live network source.
  • A feature class registered as a network source (edge, junction, or turn) becomes a controller-dataset participant: Delete/Rename are blocked (ERROR 001919) and TruncateTable is blocked (ERROR 001395, use DeleteRows instead) while the network dataset exists. There's no way to unregister a single source; the network dataset itself has to be deleted first.
  • A network dataset with VBScript evaluators opens permanently read-only starting in Pro 3.4+, with no documented in-place fix. Rebuild from scratch with Python evaluators instead.
  • Defining a restriction attribute on the network dataset does nothing by itself. It has to also be enabled in the Route/Service Area layer's Travel Mode, or it's silently ignored.
  • Editing a Field Script evaluator's code requires Force Full Build, or the edit silently has zero effect while Pro reports a clean build.
  • A Build Network that runs far longer than its usual ~90 seconds to 2 minutes is very likely blocked on a SQL Server session, not doing real work. Check Task Manager CPU (near-idle means stuck) before assuming it will finish.
