Refreshing the Street Network in QA

Prepared 2026-09-15 · Written in response to Robbie Evans's 2026-09-11 acceptance testing and Jillian Landry's direction to hold testing until the source errors are fixed

Compiled from what is committed to this repository. Verify against the live QA environment before running anything; where the two disagree, QA is the authority.

The question, answered

No. It is not as simple as truncating QA's TRNLRS_TRN_STREET_VW and loading it from Prod's. Three things are wrong with that description, and the third is the one that actually causes damage.

  1. There is no TRNLRS_TRN_STREET_VW in QA to truncate. That class only exists in Prod. QA's edge source is SDEADM.TRNLRS_network\TRNLRS_TRN_STREET, a snapshot copied from Prod's _VW at build time.
  2. TruncateTable is blocked on it anyway with ERROR 001395, because a registered network source is a controller-dataset member. DeleteRows is the supported equivalent.
  3. Reloading the edge source silently destroys all 1,180 live turn restrictions. DeleteRows + Append reassigns every OBJECTID, and turn edge references are stored as OBJECTIDs. The next build re-emits Cannot find edge element corresponding to turn identifier N for every turn and the Turns count goes to zero.

So an edge refresh is really a seven-step rebuild: sync the edge copy, re-remap the turns, verify, swap, recreate the network dataset, force a full build, re-apply the SQL grants. Roughly half a day, mostly waiting. The full procedure is below.

And before any of that: refreshing QA today would reload the same geometry Robbie just rejected. Prod's TRNLRS_TRN_STREET_VW has not changed, because nothing in the LRS has been corrected yet. See Sequencing.

Why it is not a truncate and load

1 QA has no _VW class

TRNLRS_TRN_STREET_VW is created by scripts/LRS_updates.py as a standalone SDE feature class, outside any feature dataset, and it only exists in Prod. Both 03_create_network_dataset.py and 04_sync_and_rebuild_network.py are written around that fact: script 03 always reads the edge source from a dedicated PROD_SDE_CONNECTION regardless of which environment it is building into.

What QA actually has is the feature dataset copy:

E:\HRM\Scripts\SDE\SQL\qa_RW_sdeadm.sde\SDEADM.TRNLRS_network\TRNLRS_TRN_STREET

That copy, not a _VW, is what the QA network dataset reads. The name differs because SDE enforces unique feature class names across the whole geodatabase, so the copy cannot reuse the _VW name.

Worth verifying live: if something named TRNLRS_TRN_STREET_VW does turn up in QA, it is an orphaned one-off snapshot, not a source of the network dataset. Refreshing it would change nothing about routing results. Check what the network dataset's Sources tab actually lists before touching anything.

2 TruncateTable raises ERROR 001395

TRNLRS_TRN_STREET is a registered edge source of TRNLRS_street_network, which makes it a controller-dataset participant. arcpy.management.TruncateTable against it fails with:

ERROR 001395: Operation not supported on a feature class in a controller dataset.

arcpy.management.DeleteRows is an ordinary edit operation and is supported. It is slower on a table this size, but it does not require tearing the network dataset down. 04_sync_and_rebuild_network.py already does it this way.

Known bug, relevant here: append_feature() inside scripts/LRS_updates.py still calls arcpy.TruncateTable_management() directly, and sync_network_edge_source() calls it. That will hit this exact error the first time it runs against a controller-dataset edge source. It has not surfaced only because LRS_updates.py has never been deployed to Prod.

3 The reload reassigns every OBJECTID, which breaks every turn

This is the one that matters. The chain:

  • A turn feature stores its edge references as Edge{N}FID, which is the OBJECTID of a feature in the registered edge source. That is the entire reason 05_rebuild_traffic_turns.py exists.
  • OBJECTID is database-managed and is not carried across by Append. Every reloaded row gets a fresh one.
  • So after the reload, the segment-to-OBJECTID mapping every turn depends on is gone.

The next BuildNetwork then re-emits, for all 1,189 turns:

Cannot find edge element corresponding to turn identifier 1.

and Network Dataset Properties shows Turns: 0. Nothing errors out loudly. The build reports success, the network solves fine, and every prohibited turn is silently unenforced. This project has already chased that exact regression three separate times.

Edge{N}FCID is safer but not free: it holds the edge class's DSID, which survives DeleteRows and Append (the class object persists) but changes whenever the class itself is deleted and recreated. So re-run the turn remap after anything that recreates TRNLRS_TRN_STREET, not just after its geometry changes.

Documentation correction: network_dataset_migration_plan.md's Rebuild Cadence section used to state that the turn class does not need rebuilding on each LRS refresh. That was wrong for the reason above, and has been corrected as part of this work.

4 Knock-on: the swap invalidates the SQL grants

Swapping the turn class requires deleting the network dataset first (ERROR 001919 blocks Delete and Rename on a registered source while it exists). Deleting and recreating the network dataset reassigns its registration IDs, and the PUBLIC SELECT grants go with the old ones.

QA's current IDs are N_3 and ND_40171, set on 2026-09-01. After a rebuild they will be different. Until the new ones are granted, every OS-authentication user, Robbie included, gets DBMS table not found and cannot open the network dataset at all. This is the single easiest step to forget and the one that most visibly breaks the person you are handing the network back to.

The procedure

Seven phases. Run from an ArcGIS Pro Python environment with the Network Analyst extension available. Paths shown are QA.

Phase 0 Baseline and backup

Record what QA looks like before you touch it, so that "did this change?" is answerable afterwards.

  • Network Dataset Properties: build date, source feature counts, Turns count, evaluator definitions on Length, OneWay, TrafficTurn.
  • Feature counts on all three sources.
  • The current N_<id> and ND_<id> registration IDs (expected N_3 and ND_40171).
  • Back up the current turn class. It is the only copy of any hand-authored turn edits.
import arcpy

QA = r"E:\HRM\Scripts\SDE\SQL\qa_RW_sdeadm.sde"
FD = QA + r"\SDEADM.TRNLRS_network"

for name in ["TRNLRS_TRN_STREET", "TRNLRS_street_junction", "TRNLRS_traffic_turn"]:
    print(name, arcpy.management.GetCount(FD + "\\" + name)[0])

arcpy.management.CopyFeatures(
    FD + r"\TRNLRS_traffic_turn",
    FD + r"\TRNLRS_traffic_turn_bak_20260915",
)
Open item this backup protects against: Mel's hand-authored Cogswell ramp turns. The remap in Phase 3 reads from the legacy TRN_traffic_turn class, so anything authored there is carried through, but anything authored directly against the live TRNLRS_traffic_turn is destroyed by the swap. Which of the two applies has never been confirmed. Back it up and check the backup afterwards.
Phase 1 Confirm Prod's edge source actually carries the fixes

Cheap, and it is the whole point of the exercise. If the corrections are not in Prod's _VW yet, stop here.

  • Feature count on Prod's SDEADM.TRNLRS_TRN_STREET_VW, compared to QA's current copy.
  • MODDATE range, to confirm the LRS refresh has run since the corrections were made.
  • Spot-check three or four of Robbie's actual flagged locations by FDMID and confirm the overshoot is gone.

The third check is the only one that proves anything. The first two confirm a refresh ran; they do not confirm it fixed the thing Robbie found.

Phase 2 Re-sync QA's edge copy from Prod

Do not use 04_sync_and_rebuild_network.py unmodified here. It is written Prod-only, and it rebuilds the network immediately after the sync, which is exactly what you do not want before the turns have been remapped. Do the sync explicitly instead:

import arcpy

PROD = r"E:\HRM\Scripts\SDE\SQL\Prod\prod_RW_sdeadm.sde"
QA   = r"E:\HRM\Scripts\SDE\SQL\qa_RW_sdeadm.sde"

src = PROD + r"\SDEADM.TRNLRS_TRN_STREET_VW"
dst = QA   + r"\SDEADM.TRNLRS_network\TRNLRS_TRN_STREET"

# DeleteRows, not TruncateTable -- see ERROR 001395 above.
arcpy.management.DeleteRows(dst)
arcpy.management.Append(inputs=src, target=dst, schema_type="NO_TEST")

print(arcpy.management.GetCount(dst)[0])

Expect the count to match Prod's _VW. From here until Phase 5 completes, QA's network dataset is in a broken state: the edge OBJECTIDs no longer match what the turns reference. Do not build it yet, and do not hand it to anyone.

Phase 3 Re-remap the turns and verify

Run 05_rebuild_traffic_turns.py with SDE pointing at QA and AUTO_SWAP_AND_REBUILD = False, so you get a chance to look at the result before it goes live. It writes TRNLRS_traffic_turn_staging.

Read four numbers out of the log before going further:

< 5%skip rate (last run: 4.0%)
> 95%Edge1End agreement (last run: 99.7%)
= DSIDedge source FCID matches Describe(edge).DSID
~1,189records written, from ~1,238 input

The script refuses the automatic swap below 95% agreement. If the skip rate jumps well above 4%, that is a signal in itself: the corrections in Phase 1 changed the geometry more than expected, and the skip categories in the log are worth reading before continuing.

Then run the independent verifier against the staging class:

python verify_turn_rebuild.py    # TURN_FC pointed at TRNLRS_traffic_turn_staging

All ten checks should pass clean, including check 9 (junction agreement) and check 10 (duplicate signatures). Do not swap on anything less.

Phase 4 Swap the turn class in

Order matters. The network dataset must go first, or ERROR 001919 blocks the delete and rename.

import arcpy

QA = r"E:\HRM\Scripts\SDE\SQL\qa_RW_sdeadm.sde"
FD = QA + r"\SDEADM.TRNLRS_network"

arcpy.management.Delete(FD + r"\SDEADM.TRNLRS_street_network")      # releases the lock
arcpy.management.Delete(FD + r"\SDEADM.TRNLRS_traffic_turn")
arcpy.management.Rename(FD + r"\SDEADM.TRNLRS_traffic_turn_staging", "TRNLRS_traffic_turn")
Phase 5 Recreate and build the network dataset

Two routes. Try the first one, because it is the thing this project most needs to find out.

Route A, scripted. Run 03_create_network_dataset.py against the corrected Python-evaluator template committed on 2026-09-03. Nobody has ever confirmed this works. QA's current network was built by hand; the template that broke before was the old VBScript one. Testing it here costs nothing extra and closes the top open item on the roadmap. Watch the log for "Copying into feature dataset" against the turn class: that would mean it is about to overwrite your freshly remapped turns with the raw legacy copy, and you should stop.

Route B, interactive, if Route A fails with ERROR 030386 or anything else. Right-click SDEADM.TRNLRS_network → New → Network Dataset. Add the three sources. Endpoint connectivity, one connectivity group, no elevation model. Then the three attributes:

  • Length, cost, metres, double. Python Field Script, Value !Shape!, no code block, both directions. Constant 0 for the junction, edge, and turn defaults.
  • OneWay, restriction, prohibited. Python Field Script both directions, constant False for all defaults:
# Along Digitized -- Code Block
def oneway_restricted(str_dir):
    return (str_dir or "").upper() in ("N", "FDTO", "T")

# Value
oneway_restricted(!STR_DIR!)


# Against Digitized -- Code Block   (FOTD, not FDTO)
def oneway_restricted(str_dir):
    return (str_dir or "").upper() in ("N", "FOTD", "T")

# Value
oneway_restricted(!STR_DIR!)
  • TrafficTurn, restriction, prohibited. Constant True on TRNLRS_traffic_turn, constant False on all defaults.

Then Build Network with Force Full Build checked, exactly once. Do not also click Build Network afterwards: a double build stacks two generations of system junctions, which is how a bogus 16,334 junctions / 37,728 edges showed up earlier in this project.

Two things that will waste your day if you forget them. A Field Script evaluator edit without Force Full Build has zero effect while Pro reports a clean build, because the precomputed per-edge weight tables stay stale. And a build that runs much longer than about two minutes on this network is almost certainly blocked on a SQL Server session, not working. Check Task Manager CPU first (near-idle means stuck), then ask whoever administers ms-gis-sql-q21. One of these ran for 18 hours before a DBA killed it.

If Route A worked, and only then, re-export the template afterwards with arcpy.na.CreateTemplateFromNetworkDataset and diff it against the committed one.

Alternative: run_full_network_rebuild.py wraps phases 3 to 5 and guarantees exactly one build per run. It swaps automatically without giving you the review step, and it does not do the Phase 2 edge sync, so run Phase 2 by hand first either way. Good choice once the refresh becomes routine; for the first run after 500 source corrections, do it stepwise so the remap numbers get looked at.
Phase 6 Re-apply the SQL grants under the new IDs

Do not skip this. Without it Robbie cannot open the network dataset at all. Follow network_dataset_sql_permissions.md; the audit query in its section 2b lists the IDs and their grant status in one pass.

SELECT name FROM sys.tables
WHERE schema_id = SCHEMA_ID('SDEADM')
  AND (name LIKE 'N\_%' ESCAPE '\' OR name LIKE 'ND\_%' ESCAPE '\')
ORDER BY name;

Grant SELECT to PUBLIC on the six N_<id>_* tables and the two ND_<id>_* tables under whatever the new IDs turn out to be, plus all four source classes: TRNLRS_TRN_STREET, TRNLRS_street_junction, TRNLRS_traffic_turn, and the easily-missed auto-created TRNLRS_street_network_Junctions. Re-apply the editor writes to HRM\GIS_LRS_EVENT_EDITOR if turn editing is still expected.

Then confirm with an actual add-to-map under an OS-auth connection, not by reading the grants back.

Phase 7 Smoke test before handing it back
  • Properties → Sources. Turns count must be nonzero and close to 1,180. Zero means the remap did not take and the whole refresh is void.
  • Build errors file. Open BuildErrors_<guid>.txt and confirm the GUID matches this run, not an earlier one. Expect zero Cannot find edge element corresponding to turn identifier lines; expect many harmless Standalone user-defined junction is detected warnings; expect a small number of Cannot find at junction lines and compare that count to the previous 9. If the source corrections worked, it should drop.
  • One-way, both directions. Route along a STR_DIR = 'FOTD' street: allowed direction solves clean, wrong-way direction returns ERROR 030212. Then route an ordinary two-way street (Barrington St) in both directions and confirm both are clean. The two-way control is the one that matters, because a one-way-only test cannot distinguish correct logic from an evaluator accidentally restricting everything.
  • Prohibited turn, on and off. Solve across a known prohibited movement with TrafficTurn enabled, then disabled. Different results means it is enforced; identical results means it is not, whatever the Turns count says.
Tell Robbie this explicitly when you hand it back: restrictions defined on the network dataset are not honoured by a Route or Service Area layer unless they are checked in that layer's Travel Mode (layer → Travel Mode → Edit → Restrictions). A freshly created layer's default travel mode does not pick up OneWay or TrafficTurn. Without them checked, a solve drives straight through a genuinely prohibited turn with no error. This cost a real afternoon on 2026-09-01.

A simpler option worth considering

QA's whole network is a disposable snapshot. It is not kept in sync with anything, nothing downstream depends on its identity, and the legacy TRN_street_network stays live and untouched throughout. So instead of an in-place edge refresh, the cleaner move is to delete QA's network dataset and its three source classes outright and rebuild from Prod's current _VW.

The step count is almost identical, because the turn remap, the recreate, the build, and the re-grant are all required either way. What it buys:

  • No stale-copy ambiguity. Every source is provably fresh.
  • It is the same procedure that will eventually be used to build Prod, so rehearsing it in QA has direct value.
  • It forces the CreateNetworkDatasetFromTemplate question to be answered, which is the top open item on the roadmap.

What it costs: the backup in Phase 0 becomes mandatory rather than prudent, since there is no in-place copy of any hand-authored turn edits left behind.

Open questions

  • Does anything named TRNLRS_TRN_STREET_VW exist in QA? This document says no on the basis of what the scripts assume. It has not been checked live. If one does exist, it is an orphan, but it is worth knowing about before someone refreshes it and expects routing to change.
  • How many of Robbie's roughly 500 are actually fixable in the LRS, and how long will that take? Neither the list nor an estimate exists yet. That number drives whether to batch the QA refresh or do it once.
  • Do the seven sub-metre turn-build gaps overlap Robbie's list? They are the same class of defect. If they do, the corrections may close those turn failures for free, which would show up as the Cannot find at junction count dropping below 9 in Phase 7.
  • Were Mel's Cogswell ramp turns authored against the legacy turn table or the live one? Still unconfirmed. Determines whether they survive this refresh or were already lost in the 2026-09-01 swap.
  • Is the turn-OID-stability problem being solved, or lived with? Every refresh needs a full turn remap for as long as the answer is "lived with," and that is a real operational cost once Prod is live. The three options on the table are: remap every cycle, make edge OBJECTIDs stable with a keyed update instead of truncate and reload, or store turns against a stable street key and re-derive edge references at build time. This needs a decision before Prod cutover, not after.
