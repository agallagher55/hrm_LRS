Refreshing the Street Network in QA

Prepared 2026-09-15 · Written in response to Robbie Evans's 2026-09-11 acceptance testing and Jillian Landry's direction to hold testing until the source errors are fixed

Compiled from what is committed to this repository. Verify against the live QA environment before running anything; where the two disagree, QA is the authority.

The question, answered

No. It is not as simple as truncating QA's TRNLRS_TRN_STREET_VW and loading it from Prod's. Three things are wrong with that description, and the third is the one that actually causes damage.

  1. QA's own TRNLRS_TRN_STREET_VW, even though it exists, is not what the network reads. QA's edge source is SDEADM.TRNLRS_network\TRNLRS_TRN_STREET. The current tracked QA creation script sources that copy from Prod's _VW specifically, by hardcoded design. Truncating and loading QA's own copy of the _VW would not refresh the network edge source.
  2. TruncateTable is blocked on the copy that matters anyway with ERROR 001395, because a registered network source is a controller-dataset member. DeleteRows is the supported equivalent.
  3. Reloading the edge source silently destroys all 1,180 live turn restrictions. DeleteRows + Append reassigns every OBJECTID, and turn edge references are stored as OBJECTIDs. The next build re-emits Cannot find edge element corresponding to turn identifier N for every turn and the Turns count goes to zero.

The agreed path is cleaner than an in-place edge sync anyway: delete QA's network dataset and its three source classes outright, and rebuild from Prod's current _VW. Verified against the actual scripts, that turns out to require two full build cycles, not one — nothing in this repository refreshes the edge and junction copies independently of a full network build. Full procedure below.

Correction, 2026-09-16: an earlier version of this document said TRNLRS_TRN_STREET_VW "only exists in Prod." That was wrong — the same-named standalone FC is visible in QA's own Pro Catalog too, created there by a run of LRS_updates.py against QA. It does not change the current scripted QA build path: 03_create_network_dataset.py reads Prod's copy specifically. What it does change is worth reading in full — see the note in Why it is not a truncate and load.
And before any of that: refreshing QA today would reload the same geometry that stopped acceptance testing on 2026-09-11. Prod's TRNLRS_TRN_STREET_VW has not changed, because nothing in the LRS has been corrected yet. See Sequencing.

Why it is not a truncate and load

1 QA does have a _VW, and that is exactly the trap

TRNLRS_TRN_STREET_VW is created by scripts/LRS_updates.py as a standalone SDE feature class, outside any feature dataset. Prod's copy is the authoritative one, overlaid from prod's own LRSN_Route and event tables. QA has a live copy of the same name too — confirmed 2026-09-16 in Pro Catalog against qa_RW_sdeadm.sde, sitting right alongside the other TRNLRS_* standalone classes, created by a run of LRS_updates.py against QA.

Neither the network build scripts nor this document's original framing accounted for that. The current 03_create_network_dataset.py hardcodes a dedicated PROD_SDE_CONNECTION for its edge input even when SDE_CONNECTION_UPDATE points at QA. 04_sync_and_rebuild_network.py also uses Prod, but it is explicitly a Prod-to-Prod steady-state sync and does not build QA. Therefore, QA's own _VW is not an input to the current tracked QA build path. What the QA network dataset actually reads is the feature-dataset copy:

E:\HRM\Scripts\SDE\SQL\qa_RW_sdeadm.sde\SDEADM.TRNLRS_network\TRNLRS_TRN_STREET

Script 03 creates that QA feature-dataset copy from Prod's _VW, not QA's. That still leaves the original answer standing (reason 1 in the callout above), just for a more precise reason: it isn't that there's nothing in QA named _VW to truncate, it's that the network does not reference that standalone class and the tracked QA build script does not use it as input.

What the repository can and cannot prove: the code proves what the current tracked script will do. It cannot prove that every historical QA build used this exact revision, or that nobody copied data manually in Pro. Do not use the earlier phrase "was never" as a historical guarantee. Confirm the live state with the read-only comparison in Phase 1 before deciding why QA is stale.
Confirmed, 2026-09-16: QA is a one-to-one mirror of prod, just without scheduled updates — it exists to test changes before they reach prod, not as an independent data set. LRS_updates.py is run against it manually, not on a fixed cadence, so its _VW reflects whenever someone last ran the script there, not the current state of prod. That is exactly why it is not safe to treat as a source: nothing guarantees it is current, and there is no way to tell how stale it is without checking. Still unconfirmed: whether anything else — another script, a map service, someone's ad-hoc QA session — reads QA's copy directly today. That doesn't change this procedure, since the tracked network build path does not use it, but is worth confirming before assuming it is safe to delete.
Practical risk this creates: anyone doing this rebuild by hand in Pro Catalog rather than through the scripts can now genuinely pick the wrong _VW — both exist, both have the same name, and only one (Prod's) is correct to copy from. When the procedure below says "Prod's _VW," that is not a formality.

2 TruncateTable raises ERROR 001395

TRNLRS_TRN_STREET is a registered edge source of TRNLRS_street_network, which makes it a controller-dataset participant. arcpy.management.TruncateTable against it fails with:

ERROR 001395: Operation not supported on a feature class in a controller dataset.

arcpy.management.DeleteRows is an ordinary edit operation and is supported. It is slower on a table this size, but it does not require tearing the network dataset down. 04_sync_and_rebuild_network.py already does it this way.

Known bug, relevant here: append_feature() inside scripts/LRS_updates.py still calls arcpy.TruncateTable_management() directly, and sync_network_edge_source() calls it. That will hit this exact error the first time it runs against a controller-dataset edge source. It has not surfaced only because LRS_updates.py has never been deployed to Prod.

3 The reload reassigns every OBJECTID, which breaks every turn

This is the one that matters. The chain:

  • A turn feature stores its edge references as Edge{N}FID, which is the OBJECTID of a feature in the registered edge source. That is the entire reason 05_rebuild_traffic_turns.py exists.
  • OBJECTID is database-managed and is not carried across by Append. Every reloaded row gets a fresh one.
  • So after the reload, the segment-to-OBJECTID mapping every turn depends on is gone.

The next BuildNetwork then re-emits, for all 1,189 turns:

Cannot find edge element corresponding to turn identifier 1.

and Network Dataset Properties shows Turns: 0. Nothing errors out loudly. The build reports success, the network solves fine, and every prohibited turn is silently unenforced. This project has already chased that exact regression three separate times.

Edge{N}FCID is safer but not free: it holds the edge class's DSID, which survives DeleteRows and Append (the class object persists) but changes whenever the class itself is deleted and recreated. So re-run the turn remap after anything that recreates TRNLRS_TRN_STREET, not just after its geometry changes.

Documentation correction: network_dataset_migration_plan.md's Rebuild Cadence section used to state that the turn class does not need rebuilding on each LRS refresh. That was wrong for the reason above, and has been corrected as part of this work.

4 Knock-on: the swap invalidates the SQL grants

Swapping the turn class requires deleting the network dataset first (ERROR 001919 blocks Delete and Rename on a registered source while it exists). Deleting and recreating the network dataset reassigns its registration IDs, and the PUBLIC SELECT grants go with the old ones.

QA's current IDs are N_3 and ND_40171, set on 2026-09-01. After a rebuild they will be different. Until the new ones are granted, every OS-authentication user, Robbie included, gets DBMS table not found and cannot open the network dataset at all. This is the single easiest step to forget and the one that most visibly breaks the person you are handing the network back to.

Sequencing: is a refresh even the right next step?

Worth settling before anyone spends half a day on the procedure below.

The procedure

Eight phases. Delete-and-rebuild from Prod's _VW, not an in-place edge sync — simpler to reason about, and it sidesteps the controller-dataset TruncateTable/DeleteRows dance entirely, at the cost of a second full build cycle (see Phase 3). Run from an ArcGIS Pro Python environment with the Network Analyst extension available. Paths shown are QA.

Ordered entry points: network_dataset/qa_refresh/ contains numbered scripts for Phases 0–5 and post-swap turn verification. Start with that folder's README.md; the scripts delegate to the maintained build/remap/verifier implementations rather than duplicating them. SQL grants and interactive route smoke tests remain manual and are described in Phases 6–7 below.
Phase 0 Baseline and backup

Record what QA looks like before you touch it, so that "did this change?" is answerable afterwards.

  • Network Dataset Properties: build date, source feature counts, Turns count, evaluator definitions on Length, OneWay, TrafficTurn.
  • Feature counts on all three sources.
  • The current N_<id> and ND_<id> registration IDs (expected N_3 and ND_40171).
  • Back up the current turn class. It is the only copy of any hand-authored turn edits.
import arcpy

QA = r"E:\HRM\Scripts\SDE\SQL\qa_RW_sdeadm.sde"
FD = QA + r"\SDEADM.TRNLRS_network"

for name in ["TRNLRS_TRN_STREET", "TRNLRS_street_junction", "TRNLRS_traffic_turn"]:
    print(name, arcpy.management.GetCount(FD + "\\" + name)[0])

arcpy.management.CopyFeatures(
    FD + r"\TRNLRS_traffic_turn",
    FD + r"\TRNLRS_traffic_turn_bak_20260915",
)
Open item this backup protects against: Mel's hand-authored Cogswell ramp turns. The remap in Phase 3 reads from the legacy TRN_traffic_turn class, so anything authored there is carried through, but anything authored directly against the live TRNLRS_traffic_turn is destroyed by the swap. Which of the two applies has never been confirmed. Back it up and check the backup afterwards.
Phase 1 Confirm Prod's edge source actually carries the fixes

Cheap, and it is the whole point of the exercise. If the corrections are not in Prod's _VW yet, stop here. This phase also distinguishes two different meanings of "QA is stale": QA's standalone _VW may be stale because its manual LRS refresh has not run, while the network's separate feature-dataset edge copy may be stale because the QA network has not been recreated since Prod changed.

  • Feature count on Prod's SDEADM.TRNLRS_TRN_STREET_VW, compared separately to QA's standalone _VW and QA's actual network edge source.
  • MODDATE range, to confirm the LRS refresh has run since the corrections were made.
  • Spot-check three or four of Robbie's actual flagged locations by FDMID and confirm the overshoot is gone.

The third check is the only one that proves anything. The first two confirm a refresh ran; they do not confirm it fixed the thing Robbie found.

Double-check the actual paths before deleting anything. Run this read-only snippet in the ArcGIS Pro Python environment. It confirms the path hardcoded by the current build script and compares the three live row counts and date ranges. A QA network-edge count/date range older than Prod supports the simple explanation that the QA network snapshot has not been rebuilt since the latest Prod refresh. A stale QA standalone _VW by itself does not explain the network, because the network does not reference that class.

import arcpy
import importlib.util
import sys
from pathlib import Path

script = Path(r"<repo>\network_dataset\scripts\03_create_network_dataset.py")
sys.path.insert(0, str(script.parent))
spec = importlib.util.spec_from_file_location("create_network_dataset", script)
build = importlib.util.module_from_spec(spec)
spec.loader.exec_module(build)

qa = r"E:\HRM\Scripts\SDE\SQL\qa_RW_sdeadm.sde"
datasets = {
    "script 03 edge input (expected Prod _VW)": build.STANDALONE_EDGE_SOURCE,
    "QA standalone _VW (not the network source)": qa + r"\SDEADM.TRNLRS_TRN_STREET_VW",
    "QA network edge source": qa + r"\SDEADM.TRNLRS_network\SDEADM.TRNLRS_TRN_STREET",
}

print("Script 03 target feature dataset:", build.FEATURE_DATASET)
for label, path in datasets.items():
    if not arcpy.Exists(path):
        print(label, "MISSING", path)
        continue
    count = int(arcpy.management.GetCount(path)[0])
    dates = [row[0] for row in arcpy.da.SearchCursor(path, ["MODDATE"]) if row[0]]
    print(label, "count=", count,
          "min_MODDATE=", min(dates) if dates else None,
          "max_MODDATE=", max(dates) if dates else None,
          "path=", path)
Limits of this check: matching counts and date ranges are evidence, not a byte-for-byte provenance proof; two different datasets can share those values. Confirm several known changed FDMID geometries in both Prod's _VW and QA's network edge source. Also note that simply re-running script 03 while TRNLRS_TRN_STREET already exists will not refresh it: copy_fc_to_fd() deliberately skips existing destinations. The delete-and-rebuild steps below are what force a fresh copy from Prod.
Phase 2 Delete the network dataset and its three source classes

Order matters. The network dataset must go first — while it exists, TRNLRS_TRN_STREET, TRNLRS_street_junction, and TRNLRS_traffic_turn are all controller-dataset participants and ERROR 001919 blocks deleting any of them. Once it is gone, all three become ordinary feature classes and delete cleanly.

import arcpy

QA = r"E:\HRM\Scripts\SDE\SQL\qa_RW_sdeadm.sde"
FD = QA + r"\SDEADM.TRNLRS_network"

arcpy.management.Delete(FD + r"\SDEADM.TRNLRS_street_network")    # releases the controller-dataset lock
arcpy.management.Delete(FD + r"\SDEADM.TRNLRS_TRN_STREET")
arcpy.management.Delete(FD + r"\SDEADM.TRNLRS_street_junction")
arcpy.management.Delete(FD + r"\SDEADM.TRNLRS_traffic_turn")

No TruncateTable, no DeleteRows, no ERROR 001395 — that whole dance only exists because the in-place edge-sync approach edits a controller-dataset member's rows without deleting it. Dropping the classes outright sidesteps it entirely. After this, QA's SDEADM.TRNLRS_network feature dataset is empty. That is expected, not a broken state.

Phase 3 First build cycle — fresh edge and junction copies (turns will fail; that's expected)

This cycle exists because nothing in this repository refreshes the edge and junction feature-dataset copies independently of a full network build. 03_create_network_dataset.py's copy_fc_to_fd() only copies a source if the destination does not already exist, and network creation is bundled into that same script call — there is no "just refresh the copies" mode. Since Phase 2 deleted all three sources, running script 03 now copies a fresh TRNLRS_TRN_STREET from Prod's TRNLRS_TRN_STREET_VW (never QA's — see the note in Why it is not a truncate and load) and a fresh TRNLRS_street_junction from the legacy TRN_street_junction, and — because the turn class does not exist either — a raw, unremapped copy of legacy TRN_traffic_turn. It then creates and builds the network dataset immediately, against the corrected Python-evaluator template committed 2026-09-03.

python 03_create_network_dataset.py

Expect this build's errors file to show Cannot find edge element corresponding to turn identifier N for essentially every turn, and Properties to show Turns: 0. That is not a failure to chase here — the turn class attached in this cycle is the raw, pre-remap copy, and Phase 5 replaces it. What this cycle actually verifies: that the corrected template builds cleanly end to end via CreateNetworkDatasetFromTemplate for the first time in this project (the top open item on the roadmap), and that the fresh edge/junction copies are in place. Confirm the edge feature count matches Prod's _VW before moving on.

If this fails with ERROR 030386 or anything else, fall back to the interactive wizard: right-click SDEADM.TRNLRS_network → New → Network Dataset, add the three sources, endpoint connectivity, no elevation model, and the three attributes matching the template (Length as Python Field Script !Shape!; OneWay as the Python oneway_restricted(!STR_DIR!) function on Along/Against with FDTO/FOTD respectively; TrafficTurn as a constant). Build with Force Full Build checked. If it works, re-export the template afterward with arcpy.na.CreateTemplateFromNetworkDataset and diff it against the committed one before trusting the scripted path next time.
Phase 4 Remap the turns against the fresh edge copy, and verify

Run 05_rebuild_traffic_turns.py with SDE pointing at QA and AUTO_SWAP_AND_REBUILD = False, so you get a chance to look at the result before it goes live. It requires both TRNLRS_TRN_STREET (Phase 3's fresh copy) and a current TRNLRS_traffic_turn to already exist — the raw copy from Phase 3 satisfies the second requirement, since the script only reads it for its schema (as CreateTurnFeatureClass's template) and as an integrity cross-check, not for its OIDs. It writes TRNLRS_traffic_turn_staging.

Read four numbers out of the log before going further:

< 5%skip rate (last run: 4.0%)
> 95%Edge1End agreement (last run: 99.7%)
= DSIDedge source FCID matches Describe(edge).DSID — will be a new number, since Phase 2/3 deleted and recreated the edge class
~1,189records written, from ~1,238 input

The script refuses the automatic swap below 95% agreement. If the skip rate jumps well above 4%, that is a signal in itself: the corrections in Phase 1 changed the geometry more than expected, and the skip categories in the log are worth reading before continuing.

Then run the independent verifier against the staging class:

python verify_turn_rebuild.py    # TURN_FC pointed at TRNLRS_traffic_turn_staging

All ten checks should pass clean, including check 9 (junction agreement) and check 10 (duplicate signatures). Do not swap on anything less.

Phase 5 Swap and rebuild — the second, final build cycle

With a verified staging turn class and an already-fresh edge/junction pair in place, run run_full_network_rebuild.py with --use-existing-staging. The flag is important: it tells the orchestrator to preserve and swap the exact staging class reviewed in Phase 4, rather than trying to run the turn remap again. The script confirms that staging exists, deletes the network dataset, deletes the raw Phase-3 turn class, renames the verified staging class into TRNLRS_traffic_turn, then calls script 03 again — which this time skips copying edge/junction/turn since all three already exist, and goes straight to create + build. One command, exactly one build.

python run_full_network_rebuild.py --use-existing-staging
Do not omit the flag in this workflow. Without it, the orchestrator runs 05_rebuild_traffic_turns.py to create a new staging class. Because Phase 4's verified staging class already exists, script 05 will refuse to overwrite it and stop safely. The flag is an explicit operator assertion that verification and spatial review of the existing staging class are complete; the orchestrator does not repeat those checks.

Or, to keep each step visible, the same sequence by hand:

import arcpy

QA = r"E:\HRM\Scripts\SDE\SQL\qa_RW_sdeadm.sde"
FD = QA + r"\SDEADM.TRNLRS_network"

arcpy.management.Delete(FD + r"\SDEADM.TRNLRS_street_network")      # releases the lock
arcpy.management.Delete(FD + r"\SDEADM.TRNLRS_traffic_turn")        # the raw Phase-3 copy
arcpy.management.Rename(FD + r"\SDEADM.TRNLRS_traffic_turn_staging", "TRNLRS_traffic_turn")
python 03_create_network_dataset.py    # skips copying all three sources; creates + builds only

Do not click Build Network again afterward in Pro on top of either path: a double build stacks two generations of system junctions, which is how a bogus 16,334 junctions / 37,728 edges showed up earlier in this project.

Worth knowing, not yet confirmed: every scripted BuildNetwork call in this repository (scripts 03, 04, LRS_updates.py) is a bare arcpy.na.BuildNetwork(nd_path) with no explicit force-full-build argument. It does not matter for either build in this procedure — both are the first build of a brand-new network dataset instance, so there are no stale cached weight tables to inherit, which is specifically what Force Full Build guards against. It would matter a great deal for any future in-place evaluator edit against a scripted build path (script 04's steady-state Prod sync, in particular) — nobody has confirmed whether the scripted call defaults to full or incremental.

And separately: a build that runs much longer than about two minutes on this network is almost certainly blocked on a SQL Server session, not working. Check Task Manager CPU first (near-idle means stuck), then ask whoever administers ms-gis-sql-q21. One of these ran for 18 hours before a DBA killed it.

Phase 6 Re-apply the SQL grants under the new IDs

Do not skip this. Without it nobody can open the network dataset at all. Follow network_dataset_sql_permissions.md; the audit query in its section 2b lists the IDs and their grant status in one pass. The registration IDs changed twice in this procedure — once after Phase 3's throwaway build, again after Phase 5's final build. Only grant against the IDs current after Phase 5; granting after Phase 3 wastes the step, since the network dataset gets deleted again in Phase 5.

SELECT name FROM sys.tables
WHERE schema_id = SCHEMA_ID('SDEADM')
  AND (name LIKE 'N\_%' ESCAPE '\' OR name LIKE 'ND\_%' ESCAPE '\')
ORDER BY name;

Grant SELECT to PUBLIC on the six N_<id>_* tables and the two ND_<id>_* tables under whatever the new IDs turn out to be, plus all four source classes: TRNLRS_TRN_STREET, TRNLRS_street_junction, TRNLRS_traffic_turn, and the easily-missed auto-created TRNLRS_street_network_Junctions. Re-apply the editor writes to HRM\GIS_LRS_EVENT_EDITOR if turn editing is still expected.

Then confirm with an actual add-to-map under an OS-auth connection, not by reading the grants back.

Phase 7 Smoke test before handing it back
  • Properties → Sources. Turns count must be nonzero and close to 1,180. Zero means the remap did not take and the whole refresh is void.
  • Build errors file. Open BuildErrors_<guid>.txt and confirm the GUID matches this run, not an earlier one. Expect zero Cannot find edge element corresponding to turn identifier lines; expect many harmless Standalone user-defined junction is detected warnings; expect a small number of Cannot find at junction lines and compare that count to the previous 9. If the source corrections worked, it should drop.
  • One-way, both directions. Route along a STR_DIR = 'FOTD' street: allowed direction solves clean, wrong-way direction returns ERROR 030212. Then route an ordinary two-way street (Barrington St) in both directions and confirm both are clean. The two-way control is the one that matters, because a one-way-only test cannot distinguish correct logic from an evaluator accidentally restricting everything.
  • Prohibited turn, on and off. Solve across a known prohibited movement with TrafficTurn enabled, then disabled. Different results means it is enforced; identical results means it is not, whatever the Turns count says.
Tell Robbie this explicitly when you hand it back: restrictions defined on the network dataset are not honoured by a Route or Service Area layer unless they are checked in that layer's Travel Mode (layer → Travel Mode → Edit → Restrictions). A freshly created layer's default travel mode does not pick up OneWay or TrafficTurn. Without them checked, a solve drives straight through a genuinely prohibited turn with no error. This cost a real afternoon on 2026-09-01.

Why delete and rebuild, not an in-place edge sync

Agreed 2026-09-16. QA's whole network is a disposable snapshot. It is not kept in sync with anything, nothing downstream depends on its identity, and the legacy TRN_street_network stays live and untouched throughout. So instead of the in-place edge refresh (DeleteRows into the existing FD copy, matching what script 04 does in Prod's steady state), the procedure above deletes QA's network dataset and its three source classes outright and rebuilds from Prod's current _VW.

Correction to an earlier version of this section: this used to claim the step count was "almost identical" between the two approaches. Having actually traced the script logic (see Phase 3's note), that is not true — delete-and-rebuild costs a second full build cycle that an in-place sync would not need, because none of the tracked scripts can refresh the edge/junction FD copies without also creating and building the network dataset in the same call. What it buys instead:

  • No stale-copy ambiguity, and no risk of the in-place sync accidentally touching QA's own (unrelated) _VW instead of the FD copy.
  • Sidesteps the controller-dataset TruncateTable/DeleteRows mechanics entirely — there is nothing to truncate when the class itself is deleted first.
  • It is the same procedure that will eventually be used to build Prod, so rehearsing it in QA has direct value.
  • It forces the CreateNetworkDatasetFromTemplate question to be answered on the first build cycle, which is the top open item on the roadmap — for free, since that cycle has to happen anyway.

What it costs: the extra build cycle (call it 2–10 minutes of wall time, not counting the turn remap in between), and the backup in Phase 0 becomes mandatory rather than prudent, since there is no in-place copy of any hand-authored turn edits left behind once everything is deleted.

Open questions

  • Does anything besides the network build read QA's own TRNLRS_TRN_STREET_VW directly? The freshness question itself is resolved — QA is a one-to-one mirror of prod without scheduled updates, so LRS_updates.py runs there manually and the copy's currency is never guaranteed. That confirms why the scripts never read it. What is still open is whether anything else does: another script, a map service, an ad-hoc QA session. Worth confirming before assuming it is safe to delete or ignore.
  • Does arcpy.na.BuildNetwork default to a full build when called without an explicit force-full-build argument? Every scripted call in this repository omits it. Doesn't matter for either build in this procedure (both are first builds of a new network dataset instance), but matters a great deal the next time an evaluator is edited in place through a script rather than the interactive wizard — most relevantly, script 04's Prod steady-state sync path.
  • How many of the roughly 500 flagged locations are actually fixable in the LRS, and how long will that take? Neither the list nor an estimate exists yet. That number drives whether to batch the QA refresh or do it once.
  • Do the seven sub-metre turn-build gaps overlap Robbie's list? They are the same class of defect. If they do, the corrections may close those turn failures for free, which would show up as the Cannot find at junction count dropping below 9 in Phase 7.
  • Were Mel's Cogswell ramp turns authored against the legacy turn table or the live one? Still unconfirmed. Determines whether they survive this refresh or were already lost in the 2026-09-01 swap.
  • Is the turn-OID-stability problem being solved, or lived with? Every refresh needs a full turn remap for as long as the answer is "lived with," and that is a real operational cost once Prod is live. The three options on the table are: remap every cycle, make edge OBJECTIDs stable with a keyed update instead of truncate and reload, or store turns against a stable street key and re-derive edge references at build time. This needs a decision before Prod cutover, not after.
